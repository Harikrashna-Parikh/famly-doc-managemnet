# Project: Family Digital Document Locker

Build a complete, production-quality but simple **Family Digital Document Locker** as a static web application.

The application is intended for a small private family use case where important documents such as ID cards, certificates, marksheets, licenses, insurance documents, etc. can be securely uploaded once and accessed later from a simple website.

---

# 1. ABSOLUTE REQUIREMENTS

This project MUST satisfy all of the following:

* Frontend only
* Plain HTML
* Plain CSS
* Vanilla JavaScript
* Supabase as the backend service
* GitHub Pages as the ONLY hosting platform for the frontend
* Supabase Free Plan only
* Supabase Authentication
* Supabase PostgreSQL database
* Supabase Private Storage bucket
* Row Level Security (RLS)
* Storage access policies
* Signed URLs for viewing/downloading files
* No custom backend server
* No Node.js backend
* No Express
* No PHP
* No Python backend
* No Spring Boot
* No Firebase
* No paid third-party services
* No requirement for a credit card or paid Supabase plan

The final application must be deployable as static files to GitHub Pages.

Do not introduce unnecessary frameworks or build systems.

This is extremely important because the application stores potentially sensitive personal documents.

Do NOT make the storage bucket public.

Create a PRIVATE Supabase Storage bucket.

Never expose documents through permanent public URLs.

Use Supabase Storage signed URLs for temporary access.

The browser should request access only after the user is authenticated and authorized.

Architecture:

```text

 ↓
Supabase Auth
 ↓
Authenticated Session
 ↓
PostgreSQL RLS
 ↓

 ↓
```

---

# 10. STORAGE SECURITY

Storage MUST be private.

Do not use:

```javascript
getPublicUrl()
```

for private documents.

Instead use signed URLs.

For example, conceptually:

```javascript
const { data, error } =
  await supabase.storage
    .from('documents')
    .createSignedUrl(storagePath, 300);
```

Use a short expiry such as 5 minutes where appropriate.

The application should generate a fresh signed URL whenever a document needs to be viewed/downloaded.

Do not permanently store signed URLs in the database.

Store only:

```text
storage_path
```

in the database.

---

# 11. RLS SECURITY

Enable Row Level Security on every application table that contains user/data information.

Do not rely only on JavaScript checks.

Security must be enforced by PostgreSQL RLS.

At minimum:

## Admin

Admin can:

* SELECT all relevant records
* INSERT
* UPDATE
* DELETE

## Family Member

A family member can only SELECT:

* Their own profile
* Family member records they are authorized to access
* Documents belonging to their authorized family members
* Relevant categories

Family members cannot modify documents.

IMPORTANT:

The authorization must be enforced at the database level.

Do not simply hide buttons in JavaScript and consider that security.

---

# 12. STORAGE RLS

Create Storage policies that prevent unauthorized access.

A user should only be able to access files if:

1. They are authenticated.
2. They are an admin OR
3. They have access to the corresponding family member.

Storage paths should be designed so that the policy can determine the family member ID.

Do not allow anonymous uploads.

Do not allow anonymous downloads.

Do not allow anonymous deletes.
